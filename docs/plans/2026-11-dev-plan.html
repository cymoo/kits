AI统一测试平台开发计划

打造统一的 AI 测试作业平台，测试设计、用例开发、测试执行和结果分析都在一个工具里完成。
先把通用的 Agent 能力做扎实，再按部门的实际做法把测试各环节接进来。

目标

01

通用 Agent 流程走通

一个可安装的桌面应用，日常的 Agent 用法都能覆盖。测试功能都建在这一层上，所以它要先稳。

  • 流式会话：正文、思考过程、工具调用实时展示；命令执行前确认，Agent 可以向人提问；改动可看 diff；按轮回滚暂缓（原型评审结论，见下方“范围调整”）。
  • MCP：支持 stdio 和 HTTP，现有的 mcpServers 配置直接粘贴就能用。
  • 技能：遵循 SKILL.md，内置、项目、个人三级目录。
  • 记忆：项目约定和个人偏好跨会话保留。
  • 内核默认 CodeAgent，OpenCode 用于调试和兜底。

范围调整（v3，2026-11-03 原型评审）：按轮回滚暂缓，不是高频操作，改动留在工作目录里由用户用 Git 提交或丢弃，或让 Agent 改回来，内核的 revert 接口以后需要时再接；模型网关首次引导只配一个，设置里可以加多个（如内网自建 vLLM），模型按网关分组。

02

AI native 的测试作业

按部门现在的做法把测试各环节接进来。Agent 干活，人在关键节点审核，而不是在旧流程上加个“AI 生成”按钮。

  • 测试设计：从需求出发产出测试点、风险和疑问。
  • 用例开发：生成用例，逐条审核后导出或推送到用例平台。
  • 测试执行：沿用各组现有的执行命令或 CI，统一解析 JUnit XML。
  • 结果分析：失败归类、给出证据、和上次对比。
  • 四步放在测试工作台里，可以连着跑，也可以只用其中几步。
03

易用、好用、易演进

测试同学愿意天天用，后面加功能也不用推倒重来。

  • 易用：装上就能用，首次引导十分钟内配好模型、目录和 MCP。
  • 好用：结果要靠得住，用评测集和采纳率说话，而不是凭感觉。
  • 易演进：Agent、技能、产出格式都是配置，不写死在代码里；内核走适配层，换内核不动上层；新的测试环节作为扩展加进来。

排期

前三周集中做通用能力，第三周开始搭测试工作台，后三周把测试四个环节接上去。测试设计的前期准备（试用现有工具、收集各组样本）第一周就开始，和开发并行。

技术栈

不自研 Agent 内核，不引重型组件库，配置只写一份，按内核转换。

层选择原因
桌面壳Electron + electron-vite用户的 MCP 大多是 stdio 类型，要在本机起子进程、读本地文件；密钥放系统钥匙串。平台相关的代码收在 PlatformBridge 里，以后加 Web 版不动页面。
界面React 19 + TypeScript + Vite；Tailwind CSS + Radix UI；TanStack Table和原型一致，按原型自己画，不套组件库。用例审核这种大表格用 TanStack Table，只要表格逻辑。
状态zustand + TanStack Query会话是高频事件流，用 zustand 在 IPC 回调里直接写；设置页是“请求 + 缓存”，交给 Query。
Agent 内核CodeAgent（默认）/ OpenCode，经 AgentKernel 适配器两者同源，只调公共接口，差异收在方言层。OpenCode 开源，能断点，CI 用它加 mock 模型跑契约测试。
kits 工具@modelcontextprotocol/sdk + zod，本机 MCP 服务ask_user、submit_output 定义一次，两个内核都通过 MCP 调用；结构化产出按 Agent 上配的 JSON Schema 校验。
本地存储SQLite（Node 内置 node:sqlite）+ Drizzle；Electron safeStorage不用 better-sqlite3：它是原生依赖，要为 Electron 重编，内网机器不一定装得上；node:sqlite 随 Electron 自带的 Node 24 一起来，Drizzle 1.0 有官方驱动。会话、产出、AI 原稿和人工修改、token 用量从第一天就记；以后上服务端，schema 可以平移到 Postgres。
文档转换mammoth（Word）、pdfjs-dist（PDF）需求附件先转 Markdown 再进上下文，纯 JS，不需要系统依赖。图片直接走模型的视觉输入。
测试结果JUnit XML 解析各组执行器不一样，只约定报告格式，执行命令由用户配置。
工程pnpm workspace；Biome；Vitest；Playwright；electron-builder + electron-updater三个包、两三个人，不上 Turborepo，CI 慢了再加；lint 和 format 用一套工具；UT、E2E 第一周就要能跑；内网更新用 generic provider。
评测evals/ JSONL + Node 脚本先做最小可用的，不上框架。

开发约定

人主要管两头：需求和验收。中间的原型、代码、文档、测试尽量交给 AI。

人

需求

写清楚要什么、做到什么程度算完，附上原型页面。

AI

改原型

界面改动先改 designs/app，看过没问题再写页面。

AI

开发

加载 .agents/ 里的技能，照原型实现。

AI

交付说明 + 测试

说明改了什么、怎么验收；UT 和 E2E 一起提交。

人

验收

按交付说明验收。有问题改需求或说明，让 AI 重做。

交付说明

每个 PR 附一份 docs/delivery/<模块>.md：原始需求、怎么验收、主要改动、新增依赖、已知问题。验收的人看这份文档，不用通读代码。

测试跟着代码走

UT 用 Vitest，覆盖配置转换、schema 校验、事件映射；E2E 用 Playwright，覆盖主流程。没有测试的 PR 不合，CI 不绿不 demo。

技能统一放 .agents/

开发 kits 用的技能和 Agent 定义放在仓库根目录，所有人用同一套，改动走 PR。

.agents/
├── skills/
│   ├── delivery-doc/      交付说明模板
│   ├── prototype-first/   先改原型
│   ├── unit-test/         Vitest 约定
│   ├── e2e-test/          Playwright 约定
│   └── commit-and-pr/     提交信息与 PR 描述
└── agents/
    ├── feature-dev.md
    └── acceptance.md

尽量不手改代码

代码有问题，优先改需求、说明或技能让 AI 重做；确实要手改的，在交付说明里写一句原因。手改多的地方，说明技能该补了。

新依赖先说一声

引入三方库前在群里说一下：许可证能不能商用、内网能不能装、有没有原生依赖、是不是已经有类似的库。

难点与风险

技术难点

  • SSE 事件映射和完成判定：锁定版本里事件字段是否齐全，session.idle 不可靠时用轮询兜底，断线后用消息列表补齐。
  • 权限回复：CodeAgent 和 OpenCode 的接口不一样，“本次会话始终允许”的范围两边是否一致。
  • stdio MCP 进程管理：启动失败要能看到原因和 stderr，会话结束进程要回收。
  • 测试工作台的步骤编排：每一步是一个会话，步骤之间怎么传产出、暂停后怎么续上。
风险可能的情况应对
CodeAgent 不可控 接口文档不清楚，实际行为和文档对不上；版本之间行为变化，偶发卡死或进程退出。我们没法改它的代码，排查成本高。 第一周导出 OpenAPI、抓包，按实际行为写核对清单，以清单为准；差异全部收在方言层；OpenCode 作对照，同一个问题在 OpenCode 上复现不了，基本就是 CodeAgent 的问题；锁定版本，升级前先跑契约测试；问题攒成清单，定期找 CodeAgent 那边对一次。
需求没摸清，做出来没人用 测试设计、用例开发这些环节前期了解不够，按我们自己的理解闭门造车，做出来和大家实际的工作方式对不上，同事试一次就不用了。 前两周到各组看他们实际怎么做测试设计、怎么写用例，拿真实需求和用例做样本，不只听描述。每个环节找一两位测试同学当种子用户：原型、产出格式初版先给他们看，周五 demo 请他们来，用他们的真实需求试。第 6 周试用的反馈决定下一步做什么。
定制需求太多 各组的测试流程、用例字段、平台对接都不一样，每组都提一点，主流程会被拖慢，代码里到处是分支。 只做主流程。长尾需求走扩展：用例字段改产出格式，流程差异写成技能，平台对接走 MCP，各组可以自己配。确实要改代码的进需求池，周五统一排。
做成 coding agent 通用能力越做越多，去追 Claude Code、OpenCode 的完整功能（子 Agent 编排、多工作区、插件市场、IDE 集成……），测试功能反而没时间做。 通用能力做到测试场景够用就停。内核有什么用什么，不自己补；加功能前先问一句“对测试有没有直接帮助”，没有就不做。
产出格式定不下来 测试点、用例长什么样各组说法不一，格式迟迟定不下来，后面几周的开发卡住。 格式是 Agent 上的 JSON Schema 配置，不写进代码。先按一两个组的实际做法做出来，用起来再改配置。
